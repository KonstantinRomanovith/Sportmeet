# СпортРядом

Учебная клиент-серверная информационная система для организации любительских тренировок на спортивных площадках Москвы. Сервер: Python/Flask; клиент: адаптивный HTML/CSS; хранилище: SQLite с внешними ключами и ограничениями. Проект запускается локально и не является официальным сервисом города.

## Данные и ограничения

- Основной набор: [«Спортивные площадки», ID 893](https://data.mos.ru/opendata/893). В `data/sportsgrounds_2021_source.zip` лежит архивная копия версии 7.27 от 04.10.2021, полученная через DataCrafter 23.10.2021. `scripts/prepare_seed.py` переводит BSON в `data/venues_seed.csv` и проверяет уникальность исходных идентификаторов и координаты. Используются именно строки набора, без их искусственного размножения.
- Карточки площадок содержат сайт, справочный телефон и, если в выгрузке есть содержательное пояснение, детали стоимости. В архиве заполнены 4750 сайтов, 4732 телефона и 19 содержательных пояснений к стоимости; служебные значения вроде «0» и «нет» не показываются как пояснения. Это архивные контакты 2021 года: актуальность следует уточнять. Администратор площадок может исправить эти поля с записью изменений в историю.
- Каталог площадок поднимает места с будущими опубликованными встречами наверх; фильтр «Только со встречами» показывает, где уже можно подать заявку. На главной выделена ближайшая встреча, а основная навигация и действия текущей роли доступны через компактное меню.
- Архив содержит **4751** площадку с уникальными `global_id`. В актуальной версии портала число строк и значения могли измениться. Чтобы обновить проект, следует получить новую выгрузку с data.mos.ru, проверить структуру и повторить преобразование. Скрипт текущей версии предназначен для приложенного архивного ZIP.
- Из названия площадки выделяются футбол, баскетбол, волейбол и теннис; прочие объекты относятся к общей физической подготовке. Это эвристика приложения, а не официальная классификация. Поле `ServicesSummer` в архиве одинаковое для всех объектов.
- Работа сервиса **не резервирует городские площадки**. Он предотвращает пересечения *опубликованных в приложении* тренировок на одной площадке. Вместимость тренировки назначает организатор; поле `Seats` архивного набора не используется как вместимость. Каталог 4751 площадки — справочник адресов и характеристик; заявку можно подать только на отдельную опубликованную встречу в разделе «Встречи с записью». Если встреч ещё нет, участник может предложить вид спорта и район в разделе «Предложить занятие»; подтверждённый организатор видит эти предложения и может создать встречу, после публикации которой участник получает ссылку. Предложение не является заявкой на участие. Исходная выгрузка сама по себе не содержит действующих спортивных секций и мероприятий.
- Адреса, периоды и часы работы отражают состояние архива. Перед реальным посещением их следует проверять у владельца площадки. Картографическая ссылка ведёт на OpenStreetMap.

## Запуск

**Windows, Git Bash:** распакуйте проект в новую папку и внутри `sportmeet` выполните `bash start_git_bash.sh`. Основная база `instance/sportmeet.sqlite3` уже входит в архив: 4751 площадка, 30 пользователей, четыре организации и 36 встреч (29 будущих опубликованных с записью, пять ожидающих проверки и две прошедшие). Отдельной демонстрационной базы нет. Логины и пароль — в [УЧЁТНЫЕ_ЗАПИСИ.md](УЧЁТНЫЕ_ЗАПИСИ.md), подробности — в [ЗАПУСК_Git_Bash.md](ЗАПУСК_Git_Bash.md).

Для подготовки семи настоящих снимков, проверки БД и замеров на компьютере защиты используйте [ПОДГОТОВКА_К_ЗАЩИТЕ.md](ПОДГОТОВКА_К_ЗАЩИТЕ.md).

**Ручной запуск (Linux/macOS):**

Нужны Python 3.11+ и `pip`.

```bash
python -m venv .venv
source .venv/bin/activate           # Windows: .venv\Scripts\activate
pip install -r requirements.txt
flask --app app init-db
flask --app app run
```

Откройте `http://127.0.0.1:5000`. Учётные записи каждой роли уже находятся в основной базе; при необходимости можно добавить собственную командой `flask --app app create-user`. Участник и организатор также могут зарегистрироваться в интерфейсе. Вход в администрирование — `/admin`. Повторный `import-venues` обновляет исходные сведения по `source_id`, сохраняя исправленные администратором поля и созданные тренировки.

Сайт всегда читает одну рабочую базу `instance/sportmeet.sqlite3`; любые изменения через интерфейс записываются прямо в неё и сохраняются после перезапуска. В названиях встреч нет технических приписок, но начальные записи созданы для проверки сайта и не являются подтверждёнными объявлениями о реальных занятиях. При обновлении архива с сохранением своих данных остановите сервер и отдельно скопируйте старый `instance/sportmeet.sqlite3` в новую папку вместо комплектного файла. Если вы только проверяете сайт и ничего своего не сохраняли, распакуйте архив в новую папку и используйте его базу. Команда `init-db` обновляет схему при необходимости; повторный запуск безопасен.

## Роли и рабочие процессы

| Роль | Возможности текущей версии |
|---|---|
| Гость | Поиск опубликованных встреч по виду спорта, району и свободным местам; просмотр карточек встреч; фильтрация площадок и просмотр их карточек и карты. |
| Участник | Подача заявки и просмотр её статуса, отмена заявки или записи, предложение занятия в районе с просмотром ответа, отзыв после отмеченного посещения, сообщение о неточности в карточке площадки. |
| Организатор | Запрос связи с организациями; после подтверждения просмотр предложений жителей, создание и перенос своих встреч, решения по заявкам и очереди, отметки посещения. |
| Администратор площадок | Разбор сообщений, исправление карточек с историей, скрытие и восстановление площадок, выгрузка отчёта по площадкам. |
| Администратор мероприятий | Проверка организаций, подтверждение и отзыв связей организаторов, публикация и отмена занятий, работа с участниками и модерация отзывов. |
| Глобальный администратор | Возможности обоих направлений, назначение ролей, сводные показатели и CSV-выгрузка. |

Полный перечень полномочий отображается на странице `/roles` и в личном кабинете `/account`. Права проверяются на сервере для каждого действия: например, администратор площадок не публикует встречи, администратор мероприятий не правит площадки, организатор рассматривает заявки только на свои встречи. Организации, указанные посетителями при регистрации, сначала имеют статус `pending`; администратор подтверждает организацию и отдельно связь конкретного организатора с ней, а при необходимости отзывает её. Такая проверка фиксирует решение внутри системы и сама по себе не доказывает внешнюю юридическую принадлежность.

Пароли никогда не сохраняются открытым текстом: регистрация, создание пользователя через CLI и смена пароля используют scrypt с индивидуальной случайной солью. Смена пароля и назначение другой роли завершают остальные сеансы пользователя. Стартовые аккаунты имеют общий пароль только для локальной проверки; пользователь меняет его в `/account`.

### Как показать запись от начала до конца

1. Войдите под готовыми учётными записями администратора мероприятий, организатора и участника из [УЧЁТНЫЕ_ЗАПИСИ.md](УЧЁТНЫЕ_ЗАПИСИ.md). Чтобы проверить регистрацию нового организатора, создайте дополнительный аккаунт и запросите связь с организацией.
2. Администратор открывает «Управление»: при новой организации подтверждает сначала её, затем связь с организатором. Организатор видит решение во вкладке «Мои организации».
3. Организатор находит площадку через «Создать встречу», выбирает подтверждённую организацию и задаёт будущую дату. В «Мои мероприятия» встреча пока на проверке. Администратор мероприятий **публикует её**. Теперь её видят все в «Встречи с записью» и находят через фильтры главной страницы.
4. Участник открывает встречу и нажимает «Подать заявку на участие». В «Мои заявки» сразу видно «Ожидает ответа организатора»; место пока не занято.
5. Организатор открывает «Мои мероприятия» → «Заявки: 1» и нажимает «Подтвердить» или «Отклонить». Участник после обновления «Мои заявки» увидит результат. Подтверждение занятости проверяется сервером; одновременно подтвердить больше участников, чем мест, нельзя.

Форма «Сообщить об ошибке в описании площадки» отправляет сообщение **администратору площадок** и не создаёт заявку на тренировку. Автор видит статус в личном разделе; администратор площадок может решить обращение или передать его глобальному администратору. Сервис не рассылает письма: решения доступны в личных разделах, а важные изменения — во вкладке «Уведомления».

## Расширенные возможности

- Организатор создаёт до 12 еженедельных занятий в серии. Администратор может проверить отдельную дату или все ожидающие даты серии за одно действие; если любая дата пересекается с опубликованной встречей на той же площадке, серия целиком остаётся на проверке. Можно отменить будущие встречи серии.
- При заполнении мест участник попадает в очередь ожидания. Организатор одобряет или отклоняет заявку; после одобрения первый в очереди автоматически занимает место при отмене подтверждённой записи. Нерассмотренные заявки автоматически не подтверждаются. События видны во вкладке «Уведомления».
- Каталог встреч фильтрует по дате и времени; переключатель показывает карту опубликованных встреч. Карта загружает Leaflet и тайлы OpenStreetMap через интернет, а список остаётся доступным при отсутствии связи.
- Страница организации показывает описание и открытые встречи. После начала занятия организатор отмечает присутствие подтверждённых участников; это его запись внутри приложения, а не внешняя проверка личности.
- Администратор площадок исправляет поля карточки с историей каждого изменения. Повторный импорт архивного набора не перезаписывает исправленные поля. Часы работы по архиву остаются помечены архивными.

Если опубликованных встреч нет, участник открывает «Предложить занятие», выбирает вид спорта и район. Предложение видно только подтверждённым организаторам и администраторам мероприятий. Организатор выбирает его в «Идеях жителей», создаёт встречу на площадке того же района и вида спорта и отправляет на модерацию. После публикации в разделе «Мои предложения организаторам» появляется ссылка на встречу. **Чтобы участвовать, необходимо отдельно подать заявку на этой встрече.** Предложение можно отозвать до публикации; при отмене опубликованного занятия предложение вновь открывается.

При переносе тренировки её время снова проверяет администратор, прежние заявки и подтверждения отменяются; после повторной публикации участники подают заявки на новое время. При отмене мероприятия связанные заявки тоже отмечаются отменёнными. Если карточка площадки скрыта администратором, новые заявки и подтверждения на её мероприятия заблокированы.

## Модель данных

`event_series` хранит общие параметры еженедельной серии; её даты связаны через `training_sessions.series_id`. Заявки `registrations` содержат состояния `pending`, `waitlisted`, `waitlist_approved`, `active`, `rejected`, `cancelled`; `session_attendance` хранит отметки о посещении. `notifications` связывает сообщение с получателем и при необходимости с мероприятием; `venue_edits` хранит автора и историю каждого исправленного поля.

`areas` → `venues` → `venue_hours`; `sports` ↔ `venues` через `venue_sports`; `users` ↔ `organizations` через `organization_memberships` со статусом проверки; `users`, `sports`, `areas` → `activity_requests` → опционально `training_sessions`; `users` и `organizations` → `training_sessions` → `registrations` и `reviews`; `venues` → `venue_reports`; `audit_log` фиксирует изменения. Для старых событий `training_sessions.organization_id` остаётся пустым; новые встречи требуют подтверждённую связь организатора с выбранной организацией. Повторяющиеся расписания вынесены в `venue_hours`, включая перенос из прежнего дублирующего столбца при миграции, справочники и связи используют ключи вместо дублирования названий. `source_id` сохраняет идентификатор исходного набора. Внешние ключи, уникальность пользователя на тренировке и допустимые статусы проверяются SQLite. Время вводится по Москве (`YYYY-MM-DDTHH:MM`). Классы в `domain.py` задают абстрактный контракт роли, наследуемые варианты прав и инкапсулированную проверку пересечения временных интервалов.

## Проверка

```bash
pytest -q
```

Проверки охватывают права ролей и CSRF, подтверждение и отзыв связи организатора, хеширование и смену пароля с отзывом сеансов, фильтрацию встреч, подачу и обработку заявки, вместимость, очередь, серии, посещаемость, исправление площадки и миграцию старой БД. Дополнительный перечень проверенного и ограничений — в [ПРОВЕРКА_ПРОЕКТА.md](ПРОВЕРКА_ПРОЕКТА.md). Реальные производительность и объёмы БД надо измерить отдельно на машине защиты; показатели не выдуманы.
